Dinner How? — system architecture

How the app is actually built: the components, where they run, and how data moves from a tap to a dish to a tracked event. Written to explain the system to an engineer, a co-founder, or a technical reviewer.

The one-paragraph version

Dinner How is a static single-page web app — plain HTML, CSS and vanilla JavaScript, no framework, no build step, no server of its own. The culinary engine and the knowledge base (four JSON files) ship to the browser and run entirely on the device. It's hosted as static files on Vercel (auto-deployed from GitHub). The only network calls after load are a fire-and-forget analytics ping to a Google Apps Script that appends rows to a Google Sheet. That's the whole system: everything that matters runs client-side, which makes it fast, cheap (essentially free to host), offline-tolerant, and private.

How data flows — one full round trip

1. Load. Browser fetches index.html (with the engine inlined) and the four JSON files from Vercel's CDN. Everything needed to compose is now on the device.

2. Compose. The cook taps ingredients into the basket. The engine reads their capability tags, runs the six composers, ranks and prunes, and the UI renders the winning dishes with their reasoning — all locally, instantly, offline-tolerant.

3. Act. The cook adds a dish to the basket and sends the shopping list to WhatsApp via the device's native share sheet.

4. Track. Each of those actions fires a fire-and-forget POST to the Apps Script, which appends a row to the Sheet. If it fails, the app doesn't care — the user experience never depends on it.

5. Learn. Later, a Python script reads the Sheet and prints the conversion funnel and the incremental-basket numbers — the evidence for the retailer conversation.

The deliberate choices worth defending

Choice 1 No backend, no framework.

The engine is deterministic and runs on the ingredients in front of it — it doesn't need a server. Shipping it client-side makes the app fast, effectively free to host, resilient (it works even if analytics is down), and private (no basket data leaves the device except anonymous events). Vanilla JS keeps the whole thing inspectable with no build tooling.

Choice 2 Knowledge as data, reasoning as code.

Ingredients and dishes are JSON; the judgment that reads them is code. This split means adding an ingredient is a data edit, not a code change — and a new ingredient inherits all existing behaviour through its tags. The hand-tagged knowledge base is the moat; the engine is small and stable on top of it.

Choice 3 Tracking is decoupled and honest.

Analytics is a one-way, fire-and-forget POST to a Sheet — the cheapest possible pipeline, and one that can never slow or break the app. The events mirror the real user decision (a lead vs. a conversion are logged distinctly), so the funnel is trustworthy rather than flattering.

The meat-cut model

Proteins carry a two-layer cut model so the engine knows how a cut behaves, not just its name — the difference between a stir-fry cut and a braise-only cut.

FieldWhat it encodesValues
cutThe named cut — the human labelChuck, Brisket, Short rib, Steak/Sirloin, Breast, Thigh, Shoulder, Ribs, Belly, Loin/Chop
cut_roleHow it must be cooked — the behaviourquick (thigh, breast, steak) · braise (chuck, brisket, ribs, belly)
cut_noteA short human note about the cut"steam whole — sweet, delicate white flesh"
formShape modifier that changes handlingmince

The role is backed by a capability tag the engine actually reasons over: every braise cut also carries collagen_rich, which suitsHeat reads to rule out dry-heat baking (it would be leather) and route it to slow wet heat — connecting to the collagen_breakdown reaction in the method science. The full chain: Chuck → braise → collagen_rich → needs collagen_breakdown → slow cooker / pressure cooker / long simmer. Fish, seafood and tofu skip the cut model — it's specifically the red-meat & poultry behaviour layer.

The vegetable model

Vegetables carry their own behaviour dimensions, so the engine knows what wilts, what holds up in a bake, and what makes a natural bed under a protein.

FieldWhat it encodesValues
groupThe vegetable typeleafy, root, fruiting, pods, florets, fungi, aromatic
bed_commonnessHow naturally it forms a green bed under a protein1–5 (bok choy 5, mushroom 5; watercress 2)
cuisine_affinityHow central it is to the cuisine1–3
hueIts colour — drives the generative dish arta hex colour per vegetable

As with meat, the cooking decision comes from the capability tags: leafy + water means it wilts fast (a green bed or a quick stir-fry, never a long bake), while holds_shape means it survives roasting and braising. So bok choy (leafy, water) and pumpkin (holds_shape, starchy) are routed to completely different methods without any name-based rules — the tags decide.

methods.json — the cooking science

The part most food apps don't have: methods are backed by the actual reactions cooking relies on — maillard, caramelization, collagen_breakdown, starch_gelatinization, protein_coagulation, fat_rendering, reduction, crisping — plus a time model (prep, per-appliance multipliers, passive-time caps). This is what lets the engine reason about why a cut needs a method, not just pattern-match.

appliances.json — 7 appliances

Stovetop, oven, steamer, rice cooker, pressure cooker, slow cooker, air fryer — each with its timing behaviour, so the engine only proposes what the cook can actually make.

Inside the engine

Small, deterministic, and readable — the intelligence is in the knowledge base; the engine is the judgment that reads it. Three parts:

The six composers — one per method, same signature.

steamCandidates · wokCandidates · riceCandidates · noodleCandidates · potCandidates · bakeCandidates. Each takes the basket and proposes dishes, picking a subject, choosing vegetables, and setting the rest aside with reasons.

The reasoning functions — derived properties computed from tags.

isWholeFish (fish_family and not filleted → steam only), suitsHeat (dry vs. wet), wokBehaviour, steamFormOf, pickLeadProtein (which protein leads), pickDishVeg (which vegetables go), potSpeciesWord. Each is a small rule over tags — so every decision is explainable.

The judgment tables — hand-tuned lookups the composers consult.

BROTH_BASE (which proteins make soup, and how deep), ROAST_VEG (what holds up in a bake), CHARACTER_SEASONINGS (a sauce that defines a dish), PROTEIN_LEAD_PRIORITY (who wins when two proteins compete), NOODLE_DIRS / STEAM_DIRS (the style directions per method), and the three-tier protein rule that decides belongs / unusual / excluded.

What this makes easy later

  • A native app — the engine is portable JS; it can drop into a mobile shell unchanged.
  • Personalisation / ML — the tracking already generates the training data; a small model exported to run client-side fits the no-backend shape.
  • A retailer integration — the shopping list already knows exact SKUs (buy_ids), so a "send to cart" handoff is a small addition, not a re-architecture.
  • Scale — static files on a CDN scale to any traffic with no server cost curve.
